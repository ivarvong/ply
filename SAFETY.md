# Safety argument

Everything below is enforced by a test that runs against real `git` locally. No claim here rests on reasoning alone; each has a file:line that fails if the claim stops being true.

## Threat model

1. **Hostile or broken server.** Anything on the wire is attacker-controlled: HTTP status, content-type, pkt-line framing, v2 sections, sideband bands, pack headers, object sizes, zlib streams, deltas, ref lists. Goals: crash us, hang us, exhaust memory, make us push wrong content, make us report success falsely.
2. **Hostile or careless caller.** Strings that end up inside git objects (author, message, path) or protocol command lines (ref) have no escaping mechanism in git. Goals: header injection (extra `parent` lines → silent merge), ref smuggling, path traversal, secrets leaking into telemetry.
3. **Our own bugs.** Codec errors that produce objects git accepts but with wrong content; races that lose or duplicate commits; partial state on failure.

## Protocol semantics: the fetch product space

**Status before this section existed:** the pipeline only ever issues single-object `tree:0` fetches and one full-blob fetch, and that is what the earlier suites covered. The wider `fetch` surface (multiple wants, haves, shallow state, `deepen`/`deepen-since`/`deepen-not`, `blob:limit`, `combine:`, thin packs, negotiation without `done`) was *not* verified, and the earlier text implied broader coverage than existed. The client also had two real bugs there: a negotiation round that returns only `acknowledgments` (no `packfile`) was treated as a protocol error, and a `REF_DELTA` whose base is a later delta object in the same pack fell through to the external store. Both are fixed and covered below.

**Oracles (three, independent, all local):**

1. **Bound** (`requiredAndHad` in `test/fuzz/dag.js`): for any request, `required ⊆ got ⊆ required ∪ had`, where `required` is the exact `reachable(wants) \ reachable(haves)` after the filter (haves cut at the request's shallow set, an unshallowed commit's parents added as wants, a had want's parents never walked) and `had` is everything the client declared. This is the property a client relies on: it never lacks an object it needs, and anything extra it already has.
2. **pack-objects oracle** (`test/fuzz/packobjects.js`): `git pack-objects` invoked exactly as upload-pack invokes it, in the same repo, must yield the identical object set. Exact in both server modes.
3. **Invocation capture**: `uploadpack.packObjectsHook` records the real argv and stdin upload-pack used; the fuzzer reconstructs them from the model and compares (flags exact; lists compared as sets because `send_unshallow`'s re-parse may list a parent twice).

**Dimensions enumerated** (`test/protocol.test.js`, 14,256 cells, exhaustive product; `test/fuzz/protocol.mjs`, random with DAG repos):
want kind {tip, old commit, tag, tree, blob, tip+old, tip+tree, tag+blob} × have kind {none, ancestor, old, unrelated branch, tip itself, tree, blob, tag, unknown, tip+old, old+tip} × deepen {none, 1, 2, 99, since, not} × filter {none, blob:none, blob:limit=100, blob:limit=1, tree:0, tree:1, tree:2, combine:blob:none+tree:1, combine:blob:limit=100+tree:2} × server {loose, packed without bitmap, packed with bitmap}; thin-pack, ofs-delta, done/negotiate and client-shallow state cycle deterministically across cells. Result: every non-degenerate cell is oracle-exact and invocation-exact; degenerate `deepen-since/not` requests (want older than since, want cut by not, no commit wants) are accepted only when the degeneracy predicate holds.

**What git actually does** (each item was discovered by a failing cell, then confirmed by the capture or a direct probe; none is taken from documentation):

- Two server-side object-selection modes. **Bitmap** (packed bare repo after `gc`, `pack.useBitmaps`, no deepen, filter ∈ {none, blob:none, blob:limit, tree:0, combine of those}): exact `reachable(wants) \ reachable(haves)`; a wanted tree/blob is dropped if any have reaches it. **Traversal** (everything else): commits reachable from haves are excluded plus the *tree contents of uninteresting parents of interesting commits* (`mark_edges_uninteresting`); a have on an unrelated branch excludes nothing; a wanted tree/blob is dropped only if it is literally a have (or inside a tree have). GitHub serves from bitmapped packs, so the bitmap mode is the production one for non-shallow fetches.
- `--thin` makes pack-objects pass `--objects-edge-aggressive`: cmdline haves' own trees become uninteresting too.
- `tree:N` from a commit omits depth ≥ N (root tree is depth 0); from a directly wanted tree its entries count as depth 0, i.e. it omits depth > N — *if the want is still user-given*: git filters only objects flagged `NOT_USER_GIVEN`, the commit walk flags each walked commit's root tree, and walking an earlier wanted tree flags whatever that walk reaches (it enters a subtree only while depth < N). Such a want is filtered like any tree (`dag.js userGiven`; `fuzz/usergiven.mjs` against `git rev-list --objects --filter`). `tree:N` includes blobs shallower than N; `combine:blob:none+tree:N` is the "trees only to depth N" filter.
- Shallow: the boundary is the set of commits at exactly the requested depth (even root commits), reported as `shallow` lines even when excluded by haves; boundary commits are grafted for pack-objects (parents invisible, not `--not`); the have-walk also stops at them. Client `shallow` lines cut the have-walk always; a client commit inside the window that is not on the boundary is unshallowed: its parents become wants, it becomes an extra edge, and the shallow set is not recomputed (the parents get no new depth budget).
- `do_got_oid` marks a have's direct parents `THEY_HAVE` even when the have itself was already known, and a later have already marked is dropped from the invocation. Order-dependent.
- Tag haves peel; tag wants are sent with their target; the same commit wanted directly and via its tag yields a duplicate `shallow` line (client dedupes).
- Negotiation: with `done`, `acknowledgments` is never sent; without `done`, `NAK`/`ACK`s arrive and the server may continue straight into `packfile` when ready. `negotiate()` implements rounds.
- git 2.43 `upload-pack` dies mid-response (after `shallow-info`) on degenerate `deepen-since`/`deepen-not` requests (want older than since, want cut by not, or no commit wants). Surfaced as `code: 'protocol'`.
- Server `protocol.version` config does not matter over HTTP: `GIT_PROTOCOL` from the client header wins; a server without v2 support could not be tested locally (git 2.43 only).

**Not derived, only verified:** 21 of 458 random cases and 621 of 11,880 matrix cells are "model.approx": the calibrated model over- or under-marks one or two edge-tree objects. Those cells still satisfy the bound and are pack-objects-exact and invocation-exact; the model's residual is in `mark_edges_uninteresting`'s sparse tree-walk heuristics, which I verify against git rather than reimplement.

## Codec correctness (I3 depends on these)

- Our SHA-1 == `node:crypto` for 0…3000 random bytes with random chunking.
- Our inflate == `node:zlib` for all levels −1…9 and strategies, with exact consumed-byte count, trailing junk ignored, truncation always throws.
- Our tree encoding hashes identically to `git write-tree` for names that sort differently as dir vs file (`a`, `a-b`, `a.b`, `a0`, …), unicode, spaces, leading `-`, symlinks, exec bits.
- `git pack-objects` output across 5 window/depth/compression combinations (incl. level 0 stored blocks, depth 50 chains) parses and resolves to `git cat-file` truth for every object; offsets and chain depths match `git verify-pack -v`.
- Our thin packs are accepted by `git index-pack --fix-thin` and by `receive-pack` with strict fsck.
- `filter` semantics verified against `rev-list --filter` (and corrected a wrong belief: `tree:N` includes blobs at depth < N).

- **Line merge: rebase replayed commit 2 against a blob only commit 1 had produced** — the server said `not our ref`. The merger now serves its own blobs from memory (they are already held for the push). Found by the rebase property test on its first run.
- **A pack with the same object twice** (the same merged blob in two replayed commits, or at two paths) is refused by `unpack-objects` ("tried to add buffer twice"). `uniqueObjects` before every merge/rebase/pick push.
- **Rebase kept commits that became empty**; git drops them (`--empty=drop`). Found by the property test (3 of 180 cases); fixed and the rate is now 0.
- **Rename naming**: git reports rename/delete and a followed-rename content conflict at the *target* path; we named only the source. G1 now looks at every added path across the whole tree (one-sided directories included, fetched only when a deletion is in play — which also closed a hole where a rename target in a directory only one side touched left G1 blind), and a conflicting merge lists the added paths as possible targets.
- **Version skew, measured**: all of the line merge's remaining conservative answers came from one step, the compaction re-diff that git 2.54 added (`yc/histogram-hunk-shift-fix`). git 2.43 has no such step. Built git master (2.56) as a second oracle, ported classic Myers (prepare-stage trim/cleanup, `xdl_split` with its snake heuristic and `mxcost` cutoff) and made the step a parameter: `myers` agrees with 2.56 and `skip` with 2.43 on every merge and every diff hunk, and each crossed pairing disagrees. The line merge's conservative count against a matched oracle is now 0.
- **Merge base was not git's (silent wrong merges, found by asking where our gaps were).** (1) Criss-cross histories have two best bases; git merges them into a virtual base, we picked one: a constructed case gave `f=a` where git gives `f=x`. (2) Worse, without any criss-cross: the old rule (smallest summed distance) could pick a common ancestor that is itself an ancestor of the true base — a merge whose first parent is old. Constructed: git `f=r`, old ply `f=y`, pushed. Both fixed by computing git's best common ancestors with a completeness check; criss-cross is refused. The property generator never made merge commits in history; it does now (and fails on the old code).
- **Attribute source is version-dependent, measured**: in a bare repository git 2.43 reads `.gitattributes` from HEAD's tree; 2.46 (and 2.45.3) reverted that for performance — 2.56 reads none unless `attr.tree`/`--attr-source` is set. So ply takes the source as an explicit option instead of guessing.
- **Protocol model gap (fuzzer's model of the server, not the client)**: a clock-seeded `protocol.mjs` run hit a want of a tree that was also a wanted commit's root, under `tree:4`; git omitted two objects the model required. Cause, from `list-objects.c` / `list-objects-filter.c`: filters apply only to `NOT_USER_GIVEN` objects, and the flag is set by the commit walk and by earlier wants' walks. Modelled exactly; 1,080 targeted cases equal `git rev-list`; seeds 32/33/52/236/777 × 200 clean.
- **A `-U0` oracle artifact**: `git diff -U0` trims the common tail before diffing (`xdi_diff`'s `trim_common_tail`, only at zero context); merges never do. The hunk oracle uses `-U1` and rebuilds changed lines from hunk bodies.

## Mutation testing

`npm run test:mutate` runs Stryker (command runner) over every module in `src/`. The per-mutant command is `props`, `prefix-closure`, `format-facts`, and `mutant-kill` with `PROP_N=4` (the two pack properties cap at `min(60, PROP_N)`, so `npm test` still runs 60). `pure.test.js` stays in `npm test` and in CI job `test`; it is not in the mutator command because it scans `src/` as text, and Stryker's instrumented copies no longer contain the `fail('code')` literals that scan counts. CI job `mutate` runs the full sweep on every push to `main`. On a pull request it mutates only the `src/` files the PR changed, and passes without a run when the PR does not touch `src/`. CI job `test` runs oxlint and the unit tests, including the below-hash fuzzer at `--n 20`.

`thresholds.break` in `stryker.conf.json` is the score the full run reached. A full run (locally, and CI on `main`) fails if the score drops below it. A pull request mutates only the `src/` files it changed, so that subset's percentage is not compared to the full-library break. Independently of that score, a mutant that **survives** or is **uncovered** inside a parser (`parseTree`, `readObjHeader`, `applyDelta`, `inflate`, `pktStep`, `take`, …) or in `src/bytes.js` / `src/format.js` fails the build on every run. `scripts/mutate.mjs` is what enforces both.

An equivalent mutant is justified on the line it mutates:

```js
// Stryker disable next-line EqualityOperator: both sides are the length we just checked
```

The comment names the mutator and gives a reason. `Stryker disable all`, and removing a parser file from `mutate`, are rejected by the same script. A constant nobody reads is not equivalent — pin it from `test/format-facts.test.js`, where the literals live outside `src/` so a mutated definition fails.

## Explicitly not proven here

- **GitHub itself: fetch side now exercised, push side not.** `test/live-prepare.mjs` ran the full pipeline minus receive-pack against `github.com/elixir-ai-tools/just_bash`: ls-refs, `tree:0` commit want, bare tree want, bare blob want all honored (GitHub allows any-SHA wants), no band-2 progress, 426 ms for 4 roundtrips, 314-byte thin pack for a 15.9 KB README edit. That pack was then taken through real git locally — `index-pack --fix-thin --strict` on a `git clone --bare` of the same repo (2 deltas resolved against GitHub-origin bases), `verify-pack`, oid-for-oid agreement, `git diff` = one line, strict fsck, and a real `receive-pack` on a mirror with fsck/denyNonFastForwards/index-pack path, which accepted it and then rejected a replay on the stale `old`. What remains unverified is only GitHub's policy layer on receive-pack (their fsck settings, protected branches, size caps). The same code ran under local `workerd` (above); hosted deployment belongs to [ply-web](https://github.com/ivarvong/ply-web). Differences to check with `test/live.mjs`: band-2 progress despite `no-progress`, User-Agent requirements, whether `allowAnySHA1InWant` covers tree/blob wants (it does for partial-clone lazy fetch), receive-pack `ng` reason wording for the `cas_conflict` classifier (`/failed to update ref|fetch first|non-fast-forward|lock/`).
- **Server-side attribute sources.** `$GIT_DIR/info/attributes`, `core.attributesFile`, system attributes, `merge.default` and custom merge drivers (`merge.<name>.driver`) are server configuration ply cannot see; a custom driver name is treated as `text`, as git does when the driver is not configured. Paths that are not valid UTF-8 are matched after lossy decoding.
- **Criss-cross merges are refused, not merged.** git's virtual merge base (merge-ort merging the bases recursively, conflicts and all) is not ported.
- **Merge oracles: git 2.43 (installed) and git master 2.56 (built from 47fdf220).** Line merge and diff are checked against both; the end-to-end merge/rebase suites run against 2.43 only (the HTTP test server uses the system git). Rename detection is not ported: rename shapes are conflicts (a superset), never silent wrong trees.
- **SHA-256 repos.** `object-format=sha256` is not supported. ls-refs detects a non-40-hex oid and fails with `code: 'unsupported'` before any pack is requested (unit-tested in `props.test.js`; no sha256 server round-trip).
- **Timing side channels, TLS.** Out of scope; `fetch` is the platform's.
- **Server-side resource use of a lost CAS race.** A loser's pack is unpacked before rejection. Bounded by our own push size (hundreds of bytes), but N racing writers cost the server N unpacks per round.
- **Workers runtime: now run under `workerd`** (`test/workerd.test.js`, the pipeline bundled into a Worker, fetching from the local git server). Found immediately: `fetch` captured as a default parameter and called detached throws `Illegal invocation` on workerd — every request failed before a byte went out. Node never surfaces this. Fixed by binding. Under workerd: small edit ~140 ms, 24 MB blob edit git-verified with a 1 KB push, `DecompressionStream` yields 4 KiB chunks (Node: 16 KiB) so peak per-chunk allocation is smaller; 10 concurrent writers in one isolate converge through `cas_conflict` retries (0–9 each), 11 commits, fsck clean. Not measured: production CPU-time limits (local workerd does not enforce them), subrequest limits, and real isolate memory (no heap API; our `Mem` counter is the only number).
